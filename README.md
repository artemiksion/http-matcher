# HTTP signature matcher

Rust-стенд для проверки HTTP-запросов сигнатурами Nmap. Для каждого запроса
выдаются все совпавшие имена сервисов в JSONL: `request_id`, `match`, `softmatch`.
Полный корпус: 1 114 166 запросов (1 040 242 Legitimate + 73 924 Malicious),
5 365 209 223 нормализованных байта; 11 267 поддержанных правил.

Подготовка данных, сборка, sanity-check, запуск baseline/fast, матрица воркеров
и профилирование собраны в [командах запуска](docs/running.md).
[Подробный отчёт](docs/performance.md) содержит счётчики и методику экспериментов.

## Путь запроса

Оба режима до измерения матчинга читают JSON, десериализуют и нормализуют корпус,
компилируют правила. Байты: `method + " " + URI + CRLF + headers + CRLF + body`.
Имена заголовков приводятся к ASCII lowercase, заголовки сортируются;
регистр остальных полей и NUL сохраняются. Нестроковое тело — компактный JSON,
`null` — пустое тело.

**Baseline** последовательно проверяет каждое правило каждого запроса через
`Regex::is_match`, без остановки на первом совпадении: около 12,55 млрд вызовов.
Совпавшие ID передаются общему `ResultBuilder`.

**Fast** при подготовке разбирает regex через `regex-syntax` и выводит необходимые
условия совпадения. Для каждого правила выбирается первое применимое условие
из таблицы; правила с одинаковым условием объединяются. Группы больше 128 правил
делятся на части; всего 1 779 групп. Метки корпуса и названия сервисов
не используются для выбора фильтров.

| Фильтр, в порядке выбора | Группы / правила | Что проверяется |
|---|---:|---|
| Точный примитив | 2 / 3 | Эквивалентная проверка длины или байта полностью заменяет regex |
| Литерал с хвостом | 2 / 2 | Фрагмент, фиксированное смещение и допустимый байт после него |
| Префикс | 1 574 / 10 931 | Обязательные варианты начала: дерево проверяет до четырёх байтов |
| Литералы | 194 / 322 | Общий DFA ищет фрагменты, покрывающие каждое возможное совпадение |
| Первые байты | 7 / 9 | Корзины допустимых начал; для непривязанных regex — все байты |

Альтернативы объединяются через OR: для `foo|bar` покрываются обе ветви.
Фильтр может выбрать лишнюю группу, но не должен исключать настоящее совпадение.
Общие проверки группы — минимальная длина по её правилам и объединение допустимых
первых байтов. Верхняя длина запроса не выводится: совпадение может быть подстрокой.

На каждом запросе корзины, префиксное дерево и поиск литералов отмечают кандидатов;
после общих проверок вызываются только их движки. Обычные группы используют
`RegexSet::matches`, одиночные — `is_match`, распознанные точные формы — байтовые проверки.
Каждое правило хранится в одной группе; несколько индексных ссылок дедуплицируются
битовой маской. Один запрос может выбрать несколько групп.

Извлечение литералов из regex происходит один раз при подготовке,
а поиск этих фрагментов — на каждом запросе. Для длинных запросов используются
четыре цепочки DFA в одном воркере с перекрытием границ, для коротких — один цикл.
Таблица переходов содержит прямые адреса с признаком совпадения;
Rust-проверки границ сохранены. Точные примитивы распознаются по форме regex,
например проверка длины `ventrilo` и проверка `version` со смещением MongoDB;
при неподходящей форме остаётся regex.

## Воркеры и результат

У каждого воркера полный набор правил и собственные рабочие кэши;
скомпилированные структуры и индексы общие. Свободный воркер забирает следующий
батч: до 32 запросов или примерно 64 KiB, большой запрос — отдельно.
Распределение динамическое, с учётом занятости и объёма; стоимость запроса
заранее неизвестна. Корпус обрабатывается один раз суммарно, независимо от числа воркеров.

**Приоритет probe** — порядок блоков `Probe` в файле, затем строк правил:
выбранная интерпретация ТЗ без `rarity`/`fallback` и сетевых проб.
Общий `ResultBuilder` сохраняет этот порядок внутри списков, убирает дубли;
hard `match` подавляет `softmatch` того же сервиса. Порядок запросов сохраняется.

[Пример объединения](docs/performance.md#алгоритмы-фильтры-и-результат):
если совпали soft/hard `http`, hard `ssh` и soft `smtp`,
а hard `http` расположен раньше hard `ssh`:

```json
{"request_id":7,"match":["http","ssh"],"softmatch":["smtp"]}
```

## Сохранённые результаты

13 октября 2026: Apple M3 (4P + 4E), 16 GiB, macOS 27.0.1, Rust 1.93.0.
Fast — медианы трёх полных прогонов; baseline — сохранённый одиночный того же дня.
Сборки различаются; одновременного A/B и привязки к ядрам нет.

| Режим / воркеры | Матчинг, с | Матчинг, req/s | Матчинг к baseline | Матчинг к fast/1 | Полный wall-clock, с |
|---|---:|---:|---:|---:|---:|
| baseline/1 | 787,478 | 1 415 | 1,00× | — | 812,845 |
| fast/1 | 5,117 | 217 747 | 153,90× | 1,00× | 20,752 |
| fast/2 | 2,899 | 384 386 | 271,68× | 1,77× | 18,477 |
| fast/4 | 1,633 | 682 199 | 482,17× | 3,13× | 17,339 |
| fast/8 | 1,184 | 940 970 | 665,06× | 4,32× | 16,861 |

В обоих режимах матчинг (`prepared.matching_seconds`) включает батчи, фильтры,
сигнатуры, приоритеты/дедупликацию, результаты в RAM и первичное заполнение поисковых кэшей.
Чтение/JSON, нормализация, компиляция, создание воркеров, join, сериализация,
запись/flush — вне интервала; явного прогрева и сброса кэшей ОС нет.
Полный внешний wall-clock включает подготовку и вывод:
fast/8 — **66 078 req/s и 48,21× к baseline**. Разброс матчинга fast/8: 1,159–1,468 с.

Все 30 полных выводов серии совпали с baseline: проверены упорядоченный SHA-256,
число и порядок ID, объём корпуса и исключения. Это эквивалентность на данном корпусе.
Источники: [последняя серия](docs/performance-data.json), [baseline](results/baseline.json),
[предыдущая серия](results/benchmark.json), [стадийный профиль](results/profile.json).

## Что дало ускорение и где предел

Основной выигрыш — отказ от перебора всех правил: на корпусе вызываются 43 из
1 779 групп, в среднем 10,52 вызова движков на запрос. Для 99,41% возможных пар
«запрос × группа» движок не вызывался; это не число пропущенных отдельных regex.
53 группы по 128 правил не вызывались, максимальная вызванная группа — 14 правил.
В 12,08% вызовов группа подтвердила совпадение; это не доля атак.

Главная затрата fast — поиск литералов: около 69% диагностического времени fast/1
и 59% суммы времени воркеров fast/8. Эти доли не раскладывают обычный параллельный wall-clock.
Четыре цепочки перекрывают зависимые загрузки, но не сокращают сканируемый объём.

Матчинг при 1→8 ускоряется в 4,32 раза, суммарное CPU-время растёт 5,11→8,70 с.
Ограничения L1D/execution latency растут и на P-ядрах; VM-счётчики совместимы
с восстановлением сжатых страниц. Первичное заполнение собственных кэшей
и распределение батчей добавляют издержки, их отдельный вклад не измерен.
Смешанные P/E-ядра тоже влияют; сильный дисбаланс воркеров не подтверждён.
DRAM bandwidth и L2 misses не измерены.
[Наблюдения и гипотезы](docs/performance.md#почему-масштабирование-ниже-линейного) разделены.

Выбраны четыре цепочки DFA и прямые адреса с признаком совпадения.
Восемь цепочек ухудшили fast/8; Vectorscan и отступы увеличили время;
снятие проверок границ не подтвердило выигрыш.
Большинство проб — единичные запуски прежних сборок.
[Короткая абляция](docs/performance.md#короткая-абляция) на 1 884 прогретых запросах:
без литеральной маршрутизации время выросло в 105,88 раза,
без точных примитивов — в 1,95 раза. Это эффект на выборке, не на полном корпусе.

## Совместимость и 100M / 1B

Оба режима используют одинаковые 11 267 правил Rust `regex`.
905 исключений: look-around — 685, разбор квантификаторов — 93, флаги — 82,
possessive quantifiers — 21, backreferences — 16, классы символов — 8.
Исключённые правила не входят в результаты обоих режимов;
[причины](docs/performance.md#несовместимые-правила) сохранены отдельно.
Совпадение Nmap-сигнатуры на HTTP-байтах не означает атаку или реальный сетевой сервис.

Корпус и результаты находятся в RAM. 100M / 1B при прежнем среднем размере
потребуют около 0,48 / 4,82 TB только нормализованных байтов.
RegexSet от числа запросов не растёт; растут сканирование, проверки групп и результаты.
Селективность новых данных и устойчивость короткого измерения на длинном потоке не гарантированы.

Нужны ограниченные по байтам порции, постоянные воркеры/кэши, компактные ID сервисов
и ограниченная очередь вывода с сохранением порядка и приоритетов.
Для больших тел — состояние между частями: независимый матчинг кусков
теряет совпадения на границах и меняет якоря; усечение меняет результат.
Далее — снижение стоимости литералов на байт и распределение запросов между узлами
с полным набором правил. Изолированный matcher и полный конвейер следует измерять отдельно.
[План масштабирования](docs/performance.md#матчинг-на-100m--1b).
