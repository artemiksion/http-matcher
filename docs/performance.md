Полные замеры и профили относятся к 13 октября 2026. 14 октября добавлены
разбор селективности по сохранённым счётчикам и отдельный короткий эксперимент.
[Компактный JSON](performance-data.json) сохраняет 12 обычных повторений,
сводки диагностики/счётчиков, селективность, короткую абляцию и идентификаторы сборки.

(`benchmark.json`, `summary.json`, `hardware-summary.json`) и

## Алгоритмы, фильтры и результат

Оба режима до измерения матчинга читают JSON, нормализуют весь корпус и
компилируют правила. Поток байтов:
`method + " " + URI + CRLF + headers + CRLF + body`.
Имена заголовков приводятся к ASCII lowercase, заголовки сортируются;
регистр URI, значений заголовков и тела, а также NUL сохраняются.
Нестроковое тело сериализуется в компактный JSON, `null` даёт пустое тело.

Baseline последовательно вызывает `Regex::is_match` для каждого поддержанного
правила каждого запроса без остановки на первом совпадении. На полном корпусе
это 12 553 308 322 проверки (11 267 × 1 114 166).

Fast при подготовке разбирает структуру выражений через `regex-syntax`.
Каждому правилу назначается первое применимое условие из таблицы.
Правила с одинаковым условием объединяются; группы больше 128 правил делятся.
Получено 1 779 групп. Условия выводятся из языка regex, а не из меток корпуса
или имён сервисов.

| Условие, в порядке выбора | Группы / правила | Что выводится из regex | Проверка запроса |
|---|---:|---|---|
| Точный примитив | 2 / 3 | Эквивалентная проверка длины или байта после смещения | Полностью заменяет regex |
| Литерал с хвостом | 2 / 2 | Произвольный префикс, литерал, фиксированный промежуток, непустой класс байтов | Поиск литерала и точная проверка допустимого байта |
| Префикс | 1 574 / 10 931 | Обязательные варианты абсолютного начала | Префиксное дерево проверяет до четырёх начальных байтов |
| Литералы | 194 / 322 | Каждый матч содержит хотя бы один извлечённый фрагмент | Общий автомат отмечает группы-кандидаты |
| Первые байты | 7 / 9 | Множество допустимых начал; для непривязанного regex — все байты | Индексная корзина, когда более сильного условия нет |

Альтернативы объединяются через OR: для `foo|bar` должны покрываться обе ветви.
Литералы выбираются по разнообразию байтов и длине. Фильтр может выбрать лишнюю
группу, но не должен исключать настоящее совпадение. Проверки группы используют
минимальную длину по её членам и объединение допустимых первых байтов.
Верхняя граница длины запроса не выводится: совпадение может быть подстрокой.

На каждом запросе воркер отмечает кандидатов через корзину первого байта,
префиксное дерево и общий поиск литералов. Затем проверяет условия выбранных
групп, вызывает их движки и передаёт совпавшие ID общему `ResultBuilder`.
Каждое правило хранится в одной группе; несколько ссылок из индексов
дедуплицируются битовой маской. Один запрос может выбрать несколько групп.
Обычная группа использует `RegexSet::matches`, одиночная — `is_match`.

Точные проверки распознаются по форме выражения. Например, `ventrilo`
`^.{111}` с dot-all означает длину не менее 111 байтов. Для соответствующей
формы MongoDB проверяется наличие `version`, пять промежуточных байтов и
следующий байт — цифра или точка. При неподходящей форме сохраняется regex.
Литерал с хвостом также использует точную проверку, а не приблизительный результат.

Общий DFA проходит по байтам запроса: четыре цепочки в одном воркере на длинных
запросах, с перекрытием границ; один цикл на коротких.
[Таблица переходов](../src/matcher/grouped/literals.rs) использует прямые адреса
с признаком совпадения; Rust-проверки границ сохранены.
У каждого воркера полный набор правил и собственные рабочие кэши;
скомпилированные структуры и индексы разделяются. Свободный воркер забирает
следующий батч: до 32 запросов или примерно 64 KiB, большой запрос — отдельно.
Распределение динамическое, с учётом объёма; стоимость запроса заранее неизвестна.
Корпус обрабатывается один раз суммарно, независимо от числа воркеров.

**Выбранная интерпретация приоритета probe:** сначала порядок блоков `Probe`
в файле, затем номер строки правила. Это порядок выдачи, а не остановка на
первом совпадении. `rarity`, `fallback` и сетевые пробы Nmap не моделируются.
[Общий ResultBuilder](../src/matcher/mod.rs) сортирует совпавшие правила,
убирает повторяющиеся сервисы в каждом списке; hard `match` подавляет
`softmatch` того же сервиса независимо от положения soft-правила.
Порядок запросов в выходном JSONL сохраняется.

Иллюстрация объединения, не запись из корпуса: пусть совпали все пять правил,
а блоки расположены в файле так:

| Порядок Probe | Вид правила | Сервис |
|---:|---|---|
| 1 | softmatch | http |
| 2 | match | http |
| 3 | match | ssh |
| 4 | softmatch | smtp |
| 5 | match | http |

Результат для запроса с ID 7:

```json
{"request_id":7,"match":["http","ssh"],"softmatch":["smtp"]}
```

`http` записан один раз в hard-списке, перед `ssh` по порядку их hard-правил;
ранний soft `http` удалён, `smtp` остаётся в soft-списке.
Совпадение Nmap-сигнатуры на HTTP-байтах само по себе не означает атаку
или наличие соответствующего сетевого сервиса.

## Несовместимые правила

Baseline и fast используют одинаковые 11 267 правил Rust `regex`.
905 исключений сообщаются с номером строки, сервисом, probe и причиной
в [сохранённом отчёте](../results/skipped-patterns.jsonl).
При запуске такой отчёт создаётся рядом с выводом как `<output>.skipped.jsonl`.
Совместимость со всем PCRE не заявляется; исключённые правила не входят
в результаты и измерения обоих режимов.

Группировка по последней строке сообщения в сохранённом отчёте:

| Причина | Правила |
|---|---:|
| Look-around: look-ahead / look-behind | 685 |
| Ошибка разбора десятичного квантификатора | 93 |
| Нераспознанный флаг | 82 |
| Possessive quantifiers: различие семантики с Rust regex | 21 |
| Backreferences | 16 |
| Ошибки классов символов и диапазонов | 8 |
| **Всего** | **905** |

Последние восемь состоят из пяти незакрытых классов, двух недопустимых границ
диапазона и одного диапазона с началом больше конца. Это сообщения выбранного
парсера/движка, а не утверждение, что исходные паттерны некорректны для PCRE.

Четыре отдельных полных запуска с таймерами. Проценты относятся к сумме

## Селективность фильтров

Это перерасчёт сохранённых полных диагностик 1/2/4/8 воркеров, без нового
прогона корпуса. Все счётчики вызовов и совпадений одинаковы при суммировании
по воркерам. Тип условия восстановлен исходной функцией `plan_groups`
во временной копии текущих исходников: ID и состав всех 1 779 групп сверены
с каждым сохранённым профилем. Таблица показывает условия маршрутизации,
а не типы движков RegexSet/singleton/примитив.

| Условие | Всего групп | Правил | Групп, вызванных хотя бы раз | Вызовы за корпус | Подтверждённые вызовы |
|---|---:|---:|---:|---:|---:|
| Точный примитив | 2 | 3 | 2 | 2 228 306 | 50,5853% |
| Литерал с хвостом | 2 | 2 | 1 | 347 879 | 82,4014% |
| Префикс | 1 574 | 10 931 | 2 | 1 112 398 | 0% |
| Литералы | 194 | 322 | 33 | 3 570 411 | 0% |
| Первые байты | 7 | 9 | 5 | 4 457 121 | 0,0243% |

«Вызов» учитывается после проверки минимальной длины и первых байтов группы.
«Подтверждённый» означает, что движок группы вернул хотя бы один ID правила,
до приоритетов и дедупликации сервисов. Один запрос может подтвердить несколько
групп; эти проценты не являются долей запросов или точностью классификации атак.
Для примитивов здесь уже выполняется точная проверка; для остальных условий
результат маршрутизации подтверждается движком группы.

За корпус выполнено **11 716 115 вызовов**, в среднем **10,52 на запрос**.
Из них 1 414 934 (12,08%) подтвердились; остальные 87,92% вернули пустой набор.
В 99,41% условных пар «запрос × одна из 1 779 групп» движок не вызывался:
это совместный эффект индексов и общих проверок длины/первых байтов.
Отдельный вклад каждого фильтра из этих агрегатов не выводится.

Выбранные группы содержали в среднем 25,52 правила на запрос. Это число
условных кандидатов, не число индивидуальных `Regex::is_match`: RegexSet
обрабатывает группу общим движком. Процентили количества групп на отдельный
запрос не сохранялись; по полным данным доступно только среднее.

| Правил в группе | Число групп |
|---|---:|
| 1 | 1 277 |
| 2 | 208 |
| 3–8 | 171 |
| 9–32 | 50 |
| 33–127 | 20 |
| 128 | 53 |

Средний размер — 6,33 правила; p50 = 1, p90 = 5, p95 = 23, p99 = 128
(метод nearest rank). Из одноэлементных групп 1 274 используют singleton RegexSet,
остальные три — точные предикаты. Все 53 группы по 128 правил имеют ноль вызовов;
самая большая вызванная группа содержит 14 правил. Поэтому проверки крупнейших
RegexSet не являются источником времени матчинга на этом корпусе.

Нулевая подтверждаемость префиксных/литеральных групп относится к данному входу.
Они остаются необходимыми для других запросов. Фильтры намеренно допускают лишних
кандидатов, сохраняя покрытие. Слабый фильтр первых байтов дал 4,46 млн вызовов
при 1 082 подтверждениях — кандидат для более точных проверок по структуре regex.
У примитива `ventrilo` все 1 114 140 вызовов подтвердились по длине;
для `pc-duo`/`pc-duo-gw` — 13 055 из 1 114 166, для MongoDB — 286 657 из 347 879.
Это совпадения синтетического Nmap-workload, а не идентификация сетевых сервисов.

## Выбор поиска литералов

В ранних пробах восемь независимых цепочек помогли fast/1, но ухудшили fast/8.
Vectorscan и отступы между строками таблицы увеличили время. Таблица `u16`
помогла, затем выбраны прямые адреса с признаком совпадения и четыре цепочки.
Снятие проверок границ не подтвердило улучшение параллельного throughput.
Большинство проб — по одному запуску прежних сборок; они не являются
контролируемой абляцией последнего варианта и не складываются в общий speedup.
Исходные записи — `literal_search_experiments` в
[отчёте предыдущей серии](../results/benchmark.json).

Следующие гипотезы: SIMD-префильтр, улучшение выбора литералов и уменьшение
пикового потребления памяти подготовки. Их эффект не измерен.

## Короткая абляция

14 октября 2026, Apple M3, Rust 1.93.0. Эксперимент занял 27,5 с вместе
со сборкой временного стенда. Основной matcher и release-бинарник не менялись.
Использованы те же функции планирования, фильтры, движки и `ResultBuilder`;
во временной копии отключалось по одному ускорению. При отключении маршрутизации
соответствующие группы направлялись в корзины первого байта, сохранялись
минимальная длина, первые байты, состав групп и их движки. При отключении
точного предиката группа использовала RegexSet исходных выражений.

Выборка: 1 884 запроса (1 749 Legitimate + 135 Malicious), 2 428 300 байтов,
15 небольших файлов. Из отсортированных файлов размером 50 KB–2 MiB выбирались
до 12 Legitimate и 3 Malicious, из каждого — первые записи по квоте.
Нормализованные запросы больше 64 KiB исключались; общий лимит — 16 MiB.
Максимальный принятый запрос — 44 919 байтов. Это ограниченная неслучайная выборка,
она не покрывает большие тела полного корпуса.

Каждый вариант прогревался проходом выборки. Три повторения в одном процессе,
порядок вариантов менялся на обратный; интервал собирал проходы до суммарных
50 мс или дольше, если один проход превышал этот порог. В таблице — медиана
времени одного прохода 1 884 запросов. Входят matcher и `ResultBuilder` с
сохранением результатов в RAM; чтение, подготовка, проверка результата, освобождение
результатов и запись JSON исключены. Планировщика воркеров в стенде нет.

| Вариант | Время прохода, мс | Отношение времени к control |
|---|---:|---:|
| Control: все ускорения | 7,720 | 1,00× |
| Без префиксной маршрутизации | 9,283 | 1,20× |
| Без литеральной маршрутизации | 817,361 | 105,88× |
| Примитивы длины/байта заменены RegexSet | 15,070 | 1,95× |
| Предикаты литерала с хвостом заменены RegexSet | 9,159 | 1,19× |
| Без префиксной и литеральной маршрутизации | 833,027 | 107,91× |

Для каждого прохода всех вариантов проверено совпадение полного результата
с baseline на этой выборке; baseline здесь запускался однократно для проверки,
его время не входит в таблицу. Полный baseline не повторялся.

Вывод ограничен выборкой: литеральная маршрутизация здесь предотвращает большую
работу групп, даже при высокой стоимости собственного поиска. Отношения времён
не складываются и не перемножаются в независимый вклад оптимизаций. Прогретые
небольшие данные нельзя напрямую сопоставлять с полной матрицей свежих процессов
или экстраполировать эти множители на 1,1 млн запросов. Все 18 интервалов,
разброс и исходник временного драйвера сохранены в `quick_ablation` компактного JSON;
агрегаты полной селективности — в `selectivity`.

## Аппаратные ограничения

CPU Counters — отдельные запуски для Bottlenecks, Instruction Processing
и L1D на 1/2/4/8 воркерах. Учитываются EL0 и потоки матчера. Доли time series
взвешены по длительности и ограничены интервалом работы по samples.

| Воркеры | Instruction Processing Bottleneck | Critical L1D miss | Execution latency | L1D miss events / 1000 load micro-ops |
|---|---:|---:|---:|---:|
| 1 | 48,99% | 1,31% | 3,74% | 25,22 |
| 2 | 51,04% | 2,88% | 4,28% | 26,71 |
| 4 | 51,15% | 4,25% | 5,85% | 32,38 |
| 8 | 50,02% | 6,65% | 9,33% | 39,18 |

Первый процент имеет знаменатель CPU Bottlenecks; следующие два — Instruction
Processing с непустым окном инструкций. Их нельзя складывать между режимами
или считать процентами wall-clock. Miss events на micro-ops — не точный
cache hit rate. При восьми воркерах execution latency составляет 14,49% на
E-ядрах и 4,63% на P-ядрах; critical L1D miss — 9,60% и 3,96% соответственно.

| Воркеры | Page faults процесса | Disk pageins процесса | CPU ядра ОС, с | Доля system CPU |
|---|---:|---:|---:|---:|
| 1 | 329 955 | 2 | 0,878 | 16,0% |
| 2 | 346 038 | 2 | 1,028 | 16,9% |
| 4 | 380 905 | 0 | 1,472 | 21,2% |
| 8 | 393 964 | 25 | 2,094 | 25,6% |

Окно VM приблизительное: сэмплы 10 мс вокруг жизни воркеров, с небольшим
setup/destruction. Начальный resident set около 0,8–1,1 GiB при 5,37 GB
нормализованных данных, затем он растёт. Faults, рост резидентной памяти и
одновременная декомпрессия указывают на восстановление сжатых страниц во время
матчинга. Disk pageins малы. Системные VM-счётчики не принадлежат только matcher;
CPU ядра ОС включает другие операции, его нельзя целиком приписать декомпрессии.

Дополнительные kernel-stack профили сняты для 1/8 воркеров; адреса ядра не
разрешились до имён функций, точная атрибуция декомпрессору не получена.
Аппаратный профилировщик меняет время исполнения: его длительности не входят
в таблицу throughput. Пропускная способность DRAM и L2 misses не измерены,
утверждать насыщение DRAM по этим данным нельзя.

## Почему масштабирование ниже линейного

Увеличение числа воркеров в последней серии уменьшает wall-clock: 5,12→2,90→1,63→1,18 с.
Замедляется обработка в пересчёте на затраченное CPU-время, а не весь прогон.
При переходе 1→8 ускорение составляет 4,32×. Уже на 1→4, когда преимущественно
используются P-ядра, получено 3,13×; одних E-ядер для объяснения недостаточно.

| Воркеры | Сумма CPU, с | CPU-время на запрос, мкс |
|---|---:|---:|
| 1 | 5,114748 | 4,591 |
| 2 | 5,762854 | 5,172 |
| 4 | 6,422987 | 5,765 |
| 8 | 8,696975 | 7,806 |

Число запросов одинаково; CPU-время включает выполнение и аппаратные ожидания
во время работы потока. Рост этого времени не означает, что программа повторно
обрабатывает запросы или обязательно исполняет больше инструкций: на него влияют
также скорость ядра, частота и задержки памяти.

Подтверждённые наблюдения:

- **Задержки кешей растут и на P-ядрах.** Critical L1D miss внутри Instruction
  Processing на P-ядрах увеличивается с 1,30% до 3,96% при 1→8. Поэтому изменение
  общей доли не сводится к добавлению E-ядер. L1 каждого ядра отдельный;
  прямой конкуренции всех воркеров за один L1 здесь нет. Общие L2, память,
  миграции потоков и характер доступа могут влиять на задержки; точный вклад
  этих причин не выделен, DRAM bandwidth/L2 misses не измерены.
- **Восстановление страниц входит в матчинг.** Подготовленные байты не обязательно
  остаются резидентными: наблюдаются сотни тысяч faults и рост resident set.
  CPU ядра ОС в приблизительном окне воркеров увеличивается с 0,88 до 2,09 с,
  его доля — с 16,0% до 25,6%. Это совместимо с дополнительной стоимостью
  восстановления сжатых страниц; не всё system CPU принадлежит декомпрессии.
- **Воркеры самостоятельно заполняют рабочие кэши.** Скомпилированные структуры
  общие и неизменяемые, поисковые кэши и scratch собственные. Первое использование
  происходит внутри таймера; при большем числе воркеров эта работа выполняется
  в нескольких контекстах. Её вклад отдельно не измерен. На длинном потоке
  первоначальный прогрев может лучше амортизироваться.
- **Балансировка в текущей серии работает.** Длительности работы воркеров близки;
  диапазон их wall_seconds в восьмипоточных запусках составляет примерно
  0,06–0,21 мс. Эти длительности не являются абсолютными timestamps завершения,
  но сильный дисбаланс ими не показан. Объём байтов на воркер различается:
  динамическая выдача учитывает занятость, распределение не обязано быть равным.

Другие механизмы есть в коде или возможны на системе, но их нельзя объявлять
главной причиной по имеющимся измерениям:

- Общий `next_batch.fetch_add` сериализует получение очередного индекса батча
  и передаёт владение линией кеша между ядрами. Это один атомик на батч,
  71 856 батчей на корпус, а не отдельный диспетчер всех запросов.
- Векторы, множества и строки результата требуют выделений памяти; возможна
  конкуренция аллокатора и записи в память. Сквозная доля этих издержек не выделена.
- Частоты, энергобюджет, миграции потоков и конкуренция с другими процессами
  могут менять скорость. Affinity и частоты не фиксировались. Особенно нельзя
  переносить короткий matcher-интервал в 1,18 с на длительный непрерывный запуск.
- Большой запрос является одной задачей: батчи ограничены байтами, но отдельное
  тело не делится между воркерами. Его обработка может определять окончание
  другого прогона; в этой серии крупный дисбаланс окончания не подтверждён.

Поиск литералов содержит зависимость «предыдущее состояние → адрес следующей
загрузки». Четыре цепочки помогают перекрывать загрузки в одном воркере,
но не устраняют задержки памяти и не сокращают объём сканирования.
Чтение JSON и вывод файлов находятся вне текущего matcher-интервала;
их последовательность не объясняет именно эти числа масштабирования.
В полном конвейере они могут стать самостоятельными ограничениями.
Описание категорий счётчиков и аппаратных задержек:
[Apple CPU bottlenecks](https://developer.apple.com/documentation/xcode/addressing-cpu-bottlenecks).

## Матчинг на 100M / 1B

Фиксированные правила означают фиксированные группы и скомпилированные автоматы.
Дополнительные запросы не добавляют в RegexSet правила или новые постоянные
структуры на каждый запрос. Lazy DFA имеет рабочие кэши с ограничением размера,
а не бесконечную историю обработанного корпуса.

Для набора regex библиотека указывает поиск O(m × n), где m характеризует
размер набора, n — длину входа; это не зависимость от числа запросов в корпусе.
При фиксированном наборе и прежнем распределении запросов суммарная работа
ожидается примерно пропорциональной объёму байтов и количеству вызовов групп,
плюс построению результатов. Это не универсальная гарантия одинакового throughput
для любого нового входа. [Документация RegexSet](https://docs.rs/regex/latest/regex/bytes/struct.RegexSet.html#performance).

Текущая организация исполнения не подходит для 100M / 1B: до старта матчинга
строится весь PreparedCorpus и массив результатов на все запросы. Такой объём
не умещается в доступные 16 GiB RAM; сжатие/подкачка резко увеличат стоимость
доступа либо процесс столкнётся с нехваткой памяти ещё при подготовке.
Это ограничение способа исполнения, а не неспособность автомата проверить
миллиард последовательных запросов.

После перехода к ограниченным порциям остаются ограничения самого матчинга:

1. **Объём сканирования.** При среднем размере текущего запроса 4 815 байтов
   100M / 1B дают около 0,48 / 4,82 TB нормализованных байтов. Поиск литералов
   проходит по этим байтам; проверки выбранных групп могут читать их повторно.
   Это логические объёмы, не измеренный DRAM-трафик. Нужны уменьшение числа
   инструкций/переходов на байт и более точные необходимые фильтры; простое
   увеличение числа воркеров не уменьшает объём работы.
2. **Состав запросов.** Средние 10,52 вызова групп и максимум 14 правил в вызванной
   группе относятся к текущему корпусу. Более длинные тела и другие данные
   могут выбрать больше групп и чаще задействовать дорогие правила. Полноту
   сохраняют фильтры, выведенные из regex; исключать правила на основании нуля
   совпадений в старом профиле нельзя. Настройка кэшей и групп требует проверки
   на новом распределении длин и кандидатов.
3. **Длительность отдельного запроса.** Один большой запрос занимает одного
   воркера и может задерживать упорядоченный вывод. Независимый поиск по кускам
   неэквивалентен поиску целиком: теряются совпадения через границу и меняются
   якоря начала/конца. Если тело нельзя хранить целиком, нужен потоковый движок
   или адаптер, сохраняющий состояние поиска и ID совпавших правил до конца
   запроса. Фиксированное перекрытие недостаточно для regex с неограниченными
   промежутками. Итоговое разделение hard/soft выполняется после полного запроса.
4. **Результат на каждый запрос.** Миллиард повторений создания векторов,
   HashSet и копирования имён сервисов добавляет работу независимо от скорости
   DFA. Стоит хранить ID сервисов, переиспользовать рабочие буферы дедупликации
   и преобразовывать ID в имена при сериализации, сохраняя порядок probe и
   подавление softmatch. Приоритеты/дедупликация остаются частью matcher-метрики;
   сериализация и запись — вне её, как и для baseline.
5. **Устойчивая производительность.** Скорость короткого прогона не подтверждает
   скорость многочасового потока. Если подача превышает устойчивую пропускную
   способность, очередь растёт. Нужны ограничение очередей по байтам,
   backpressure и, при необходимости, несколько узлов с полным набором правил,
   которым запросы распределяются однократно по объёму и ожидаемой стоимости.

Для исполнения по порциям нужно сохранить пул воркеров, скомпилированные
структуры и поисковые кэши между порциями, а результаты освобождать после
упорядоченного вывода. Хранение компактных ID и ограничение reorder-буфера
не устраняют необходимость обработать все байты каждого запроса. Модель
прерывания и возобновления длинного прогона должна сохранять позицию/ID, чтобы
не начинать весь корпус заново после сбоя.

Чистая арифметика при сохранении измеренных 940 970 запросов/с даёт 106 с для
100M и 1 063 с (17,7 мин) для 1B только на matcher. Это оценка при прежних
данных и неизменной скорости, не результат эксперимента; чтение, подготовка
и вывод здесь не посчитаны. Больше одинаковых запросов может лучше амортизировать
прогрев кэшей, но изменение входа, память и длительная нагрузка могут ухудшить
скорость. Обязательного сверхлинейного замедления от одного лишь количества нет.

Изолированный matcher-бенчмарк следует выполнять на заранее подготовленных
ограниченных порциях с одинаковыми границами времени для baseline/fast.
В реальном конвейере JSON-нормализация и вывод могут идти параллельно, однако
даже вне таймера они конкурируют с matcher за CPU и память. Для оценки такого
конвейера нужна отдельная метрика полного throughput, а не сумма пересекающихся
стадий. Новые большие прогоны для этого описания не запускались.

## Проверка результата и воспроизведение

Все 30 полных выводов серии совпали с baseline: 12 обычных, 4 со стадийными
таймерами, 12 CPU Counters и 2 с kernel stacks. Проверяются полный упорядоченный
SHA-256, число и порядок ID, запросы/байты, поддержанные/исключённые правила
и хеш отчёта исключений. Это проверка на данном корпусе.

Команды подготовки, сборки и повторения матрицы собраны в
[инструкции запуска](running.md#benchmark-и-диагностика);
аппаратное профилирование и обработка сохранённых трасс —
в [отдельном разделе этой инструкции](running.md#аппаратное-профилирование).

Аппаратный профилировщик требует macOS и Xcode/Instruments.
Существующие трассы нельзя смешивать с другим бинарником; для новой серии
нужен отдельный каталог отчётов. Скрипт сохраняет raw traces, XML, метрики
приложения и мониторинг VM. `summary.json` и Markdown-сводка последней сессии
собраны отдельно из этих отчётов; точная копия этого документа автоматически
не генерируется.
Последние стадийные данные доступны также в [results/profile.json](../results/profile.json).
